**评审对象**：用户提供的《Intent-Driven Web Test Harness（IDWTH）Skill-First 产品需求文档 V1.2》（评审稿）。
产品思路：Intent → Contract → 确定性执行（优先）/ JEV 语义决策与修复（按需）→ Evidence → 独立 Oracle → Verdict；7 个核心 Skill；三态判定。

### 总评
方向对、边界比同类项目清楚，**可以进评审**，但有 1 处架构级互斥需先定稿 + 2 处隔离保证不硬 + 13 项具体问题 + 验收标准需从 1 条扩到 9 条 + 5 个开放问题可直接关闭。

**值得保留的亮点**：①三句边界（Playwright 管稳定执行 / JEV 管选动作 / Evidence+Oracle 管对错）②P0 那条对抗性验收「JEV 认为完成但 HTTP=500 → 必须 FAIL」是全文含金量最高的一行 ③JEV 输出限定 `operation + target_index`（与 `jev-ultrafast` 的 `validate_choice` 一致）④**§19「同一套 Skills 可被不同 Agent Harness 与 CI Runtime 复用」——这是我们此前方案没有的视角，比我们更强** ⑤Freeze the Strategy + 不强制 V1 做 GEPA，收敛得当。

### ★ 架构级问题 1：互斥（P0 阻塞）
§0「可被 **Agent 加载**的 Skills」⟷ §12「确定性路径禁止调用模型」/ §13「Semantic Invocation Rate ≈ 0」。
模型编排本身每 case ≥ 1 次调用 → 两句互相否定，P0 验收无法写。
**解法（保留 skill-first 原意）**：拆两种 Runtime ——
- **Agent Runtime**：编排者是 LLM，每 case ≥1 次模型调用，用于开发/调试/探索，**不适用** §12 预算，产物不进 CI。
- **CI Runtime**：编排者是**确定性代码**，仅 L3 语义动作按需调模型，**§12/§13 全部适用**，是 **P0 验收唯一对象**。
这样保住「skills 跨 harness 可移植」，同时让「零模型调用」可验收。

### ★ 架构级问题 2：Oracle 是 Skill，但隔离不硬
两个漏口：①**调用权**在编排者手里 → 可以"这步不跑 Oracle" = **PASS by omission**；②**写入权**可被中介 → 转述时改写 verdict。
**解法（三独占）**：Oracle 的实现形式无所谓（可封装为 skill），但 ①判定逻辑的**调用权**归 Runtime 独占 ②verdict 的**写入权**归 Runtime 独占 ③verdict 必须是**纯函数** `f(evidence, assertions)`，可用归档 evidence 离线重算。
→ 顺带解决「Oracle Accuracy 怎么度量」：离线重算 + 人工抽样。

### ★ 架构级问题 3：Replay 的「Drift 修复」破坏可比性
必须拆：`replay --verify`（**默认**，零模型，漂移即**报错终止**并记 `BLOCKED(drift)`，可用作门禁）/ `replay --heal`（显式开启，产 recovery 审计 + 新版 frozen strategy，**不得用于 CI**）。
依据：*"State drift is reported instead of silently adapting the trace."*

### ★★ 对上一轮结论的重要修正（自我纠正）
上一轮我在 `product-definition.md` 写过"执行/断言/判定/取证/写盘/回放**必须落代码**，只有创作/解读/分诊类适合 skill"。
**本 PRD 促成修正**：*「做成 skill」与「确定性」不是对立属性 —— Skill 只是**封装形式**，确定性是**实现属性**。真正的判据是「**调用权与写入权在谁手里**」。*
→ 判定**可以**封装为 skill，只要 Oracle 的调用权与 verdict 写入权独占归 Runtime。这也解释了为什么 PRD 的"7 个 skill"并不必然违反隔离原则 —— 前提是编排者为确定性 CI Runtime（即问题 1 必须先定稿）。

### ★ 指标：单 case 稳定性不组合（用数学，别靠感觉）
`suite 绿灯率 ≈ p^n`（p=单 case 一致性，n=case 数，独立近似）：

| p | n=20 | n=50 | n=100 |
|---|---|---|---|
| 0.95 | 35.8% | **7.7%** | 0.6% |
| 0.99 | 81.8% | 60.5% | 36.6% |
| 0.999 | 98.0% | 95.1% | 90.5% |

PRD 写"单 case 一致性 ≥ 95%"却同时声称"可进 CI 门禁" → **自相矛盾**：50 case 的 suite 只有 7.7% 绿灯率，门禁 92% 时间在红。
反推：n=50 要 95% 绿灯率 → 单 case 必须 **99.9%**（`0.95^(1/50)`）。
**正确写法**：①**「无 flaky case」二值硬门禁**（任一 case 连跑 N≥10 次结论不一致即判缺陷）②suite 绿灯率只作观测。
**通用原则**：凡"多 case 组合"指标都要问"它怎么组合"。线性指标（成本/耗时）可平均；**比例型通过率不能，必须取幂或改二值计数**。

### ★ 5 个开放问题的建议答案
1. **置信度阈值 → 按可逆性分级，不要单一阈值**：可回退动作（点击/导航/滚动）≥**0.60**；不可逆动作（提交/删除/创建）≥**0.90** 且不达标直接 BLOCKED。依据 `JevTest` 默认 0.6。**另注**：阈值只在合法性校验之后生效 —— 响应须满足 `choice ∈ criteria`、`probability keys == criteria keys`、`Σp ≈ 1`、`p[choice]==max(p)`，否则**零动作派发**（`jev-ultrafast` 的 `validate_choice`）。
2. **K8s Adapter → V1 Core 不内置，但 M3 前提供 reference adapter（放 examples/ 不是 core）**；契约侧把 `backend:` 抽象为**可替换的 evidence provider**，不硬编码 K8s 语义。
3. **多语言 Intent → V1 不做功能，但 Schema 必须语言无关 + 预留 `locale` 字段**。自由文本字段语言无关；结构化断言字段固定英文（机器判定部分不能多语言）。
4. **Recovery 失败 → 必须 BLOCKED，不可配置为 FAIL**（语义必然，不是开放问题）：FAIL 前提是"执行完成但结果不符"，需要确定性断言失败作为证据；recovery 失败意味着动作没执行成功 → 无观测事实 → 不满足 FAIL 前提。若允许 FAIL 就是把"工具能力不足"记成"应用有缺陷"。可配置的只是 CI 是否把 BLOCKED 也阻断合并（退出码仍 2），verdict 语义不许变。
5. **GEPA 反思 → V1 不做，但 P0 就留对接口**：Trace 必须含五元组 `(intent, 页面可观测状态, JEV 请求/响应原文, 决策, 结果)` + 无损去重 + 字节上限。**反思产物必须是一版新的 frozen strategy 经人工确认后替换，不得运行时自改；反思可改 Recovery 策略，绝不可改 Goal/Assertion**（否则绕过 §8.2 的禁令，Freeze 名存实亡）。

### 建议的 5 项阻塞决议
CI Runtime 为 P0 唯一验收对象 / Oracle 调用与写入权归 Runtime + verdict 为纯函数 / 拆分 replay verify+heal / fixtures 引入 runId / 稳定性改为"无 flaky case"硬门禁。

**技能更新**：`ai-e2e-test-framework-audit` 新增「**第八步：审计 Skill-first / Agent-first 架构的三个必查点**」（编排者归属 + 判定权三独占 + 稳定性指标可组合性的数学表），并在「必查的工程细节」补入 runId 命名空间、目标歧义、BLOCKED 子类、Exit Code 契约、replay verify/heal、recovery 步级后置条件、iframe 误排除共 7 条检查项，扩充 frontmatter 触发词。

## IDWTH 详细设计 V1.0 → V1.1 优化（同项目，第二轮）

**交付物**：`20260922-jev-bs-e2e-research/final/detailed-design.md`（V1.1，**替换版**，非增补）

**优化对象**：用户提供的《IDWTH 详细设计文档 V1.0》。产出 26 项修订（A 级架构 9 / B 级可实现性 11 / C 级一致性 6）。

### ⛔ 最致命（V1.0 新引入，PRD 层看不到）：Contract 里根本没有定位声明
`steps: string[]` 只有自然语言，`assertions.dom[].selector` 标注"仅确定性路径使用" → **`has_stable_locator(step)` 恒返回 false** → 所有 step 都走语义路径 → **「Deterministic First」与「SIR ≈ 0」在数据模型层就不成立**。这是"承诺写了、代码里没有落点"的典型。

**修法（关键设计洞察）**：
- Contract 里**不应该也不允许**有 selector（新增加校验规则：`target` 出现 `#`/`.`/`//`/`>>`/`()` 即拒绝），用户写的是**语义 target**（`"创建按钮"`）。
- 所以判据不是"有没有 locator"，而是**"语义 target 能否被无歧义确定性解析"** —— 这是**运行期解析结果**，不是 Contract 的静态属性。
- 新增 §3.3「定位解析模型」：`resolveTarget()` 返回 `ResolvedTarget{elementId, strategy, matched, confidence, observationId}` + `ResolveResult` 四态（resolved/ambiguous/not_found/unavailable），**取代 `has_stable_locator`**。
- **`ResolvedTarget` 同时是确定性路径与模型路径的统一中间表示** → `execute(action)` 一份实现即可服务两条路径（V1.0 缺这一环，确定性路径的 Playwright Locator 在模型里没有位置）。

### ⛔ 第二致命：「歧义」被当成「未命中」→ 假 PASS 头号通道
V1.0 伪代码 `if has_stable_locator ... else semantic` 会把 `matched > 1` 往下交给模型猜一个。
**硬规则**：**歧义 ≠ 未命中**；`matched > 1` 立即 `BLOCKED(ambiguity)`，**不降级、不取第一个、不交给模型**。

### ⛔ 第三致命：对 irreversible 动作失败做 recovery = 重复副作用
V1.0 `if result.failed: recovery` 无条件触发 → 对着"提交失败"再点一次提交，在 CMDB/K8s 上是**真实损害**。
**修法**：Contract 的 step 新增 `risk: reversible | irreversible`（**由 Contract 声明，模型无权降低**）。
- `irreversible` 失败 → 直接 `BLOCKED(decision)`，**禁止 recovery、禁止重试**
- `ambiguous` / `timeout` / `nav_blocked` 也**一律禁止 recovery**
- 新增 `ActionResult.dispatched` 字段 —— 这是 *"A dispatched mutation can have an unknown outcome. Never repeat it automatically."* 的**可执行形式**（没这个字段，"不得重试"在代码里无法表达）

### Skill 的物理形态（V1.0 完全没回答，导致 skill-first 无法工程化）
**Skill = 可校验的契约声明，不是可执行的程序**，分三层：①声明层 `SKILL.md` ②实现层（确定性代码，`runtime/`+`tools/`）③调用层（Runtime 独占的 4 个点）。
由此 7 个 skill 分两类 —— **这就是双 Runtime 的落法**：
- **知识型**：`web-test-contract` —— 仅 **Authoring 阶段**运行一次，**CI Runtime 不调用**（产物是 Frozen Contract）
- **契约型**：其余 6 个 —— Runtime 期由确定性代码实现

### 其他 A 级 / 重要修正
- **Oracle 权限**（决议 2 未落地）→ Runtime **四独占**：Oracle 调用权 / verdict 写入权 / **Freshness 校验权** / cleanup 执行权（+ Credential 解析权）。
- **Trace 权威源**：`oracle_result.verdict` 为唯一权威（顶层 `verdict` 改名 `verdict_snapshot` 标注"派生显示"）+ `verdict_hash = sha256(oracle_result ‖ evidence_digest)`；新增 CLI `idwth oracle recompute <run_id>` 让"离线重算"可验收（A8）。
- **★ Evidence 必须按「是否参与判定」分级，不按体积分级**：`judgement_set`（参与断言的证据 + issues + recovery + JEV 原文）**永不截断**；`archived`（截图/完整 DOM/console）可外移。V1.0 的"超限归档并拒绝截断"自相矛盾 → 若裁掉判定必需集，决议 2 的离线重算即不成立。**这是可复核性的物理下限。**
- **断言语义精确表**（V1.0 完全缺失，Oracle 因此不可实现）：7 原语逐条给"精确语义 / 匹配规则 / **无法求值时**"。**关键**：`visible` 求值为否 = **FAIL**（可观测事实）；`value/checked/number` 目标不存在 = **BLOCKED(evidence)**（无法求值）—— 这就是"复杂度不足即 BLOCKED"在断言级的落点。
- **Oracle 判定四步优先级（不可换序）**：①任一 required 断言无法求值 → BLOCKED(evidence) ②任一目标歧义 → BLOCKED(ambiguity) ③任一断言 false → FAIL ④全过 → PASS。
- **frozen strategy artifact**：`contract_hash` 绑定（Contract 改了整体失效）、**只接受人确认写入**、**`confirmed_runs >= 2` 且连续 2 次成功才可入指纹**（防一次运气污染）。
- **replay 拆 `--verify`（默认，零模型，漂移即终止）/ `--heal`（显式，产物不入 CI）**（决议 3 落地）。
- **recovery 上限**：1 次/step、**3 次/case** —— 否则 recovery 链掩盖定位层系统性失效。
- **退出码六值**：`0 PASS / 1 FAIL / 2 BLOCKED / 3 CONFIG_ERROR / 4 RUNTIME_ERROR / 130 取消`。**把 CONFIG_ERROR 从 BLOCKED 拆出**：两者对使用者含义相反（看系统 vs 看用例），混用会虚高 `BLOCKED 占比 < 15%` 指标。
- **SIR 分母必须是 step 不是 case**：否则一个 10 步 case 只调 1 次模型，SIR 显示 1.0，指标失去意义。
- **延迟三口径分列**：决策延迟（L3 段 + JEV 往返，≤2s）/ 动作超时（30s）/ 断言 deadline（5s，轮询 100ms），互不包含。
- 新增两条 Contract 校验规则：**`risk: irreversible` 的 step 必须有 `postcondition`**（A9 的防线）；**`target` 禁止 CSS/XPath/JS 语法**。
- 新增模块 `runtime/resolve.ts` + `runtime/freshness.ts` + `schema/strategy.schema.json`；新增 CLI `idwth oracle recompute` / `idwth doctor`。
- 9 条对抗性验收全部归位到模块与里程碑（M1: A3/A8｜M2: A1/A2/A4/A5/A7｜M3: A9｜M4: A6）。
- 开放问题 4 → **2 项**（置信度阈值、Recovery 失败已在 PRD 评审关闭，V1.0 仍在提问 = 未吸收评审）。

### 与 `jevharness-review.md`（本工作区另一份产出）的交叉整合
发现工作区内已有 `final/jevharness-review.md`（JevHarness 源码级评审，即 PRD 里「JevHarness 模式」的来源，`license: null` 只可取设计），据其 §7.1 的 P0 建议补入两处：
- **★ frozen strategy 绑定从单一 `contract_hash` 升级为「五重绑定」**：`contract_hash` / `strategy_hash` / **`oracle_impl_hash`** / `runner_version` / `env_fingerprint`，并进入 `verdict_hash`。
  **`oracle_impl_hash` 是我原稿漏掉的一环，且是本轮最有价值的补入**：前四条都在保护**执行**（Contract/指纹/环境），唯独漏了**判定器本身**。判定器一改（修断言口径、加 `text_contains`），① 新旧 verdict **不可比**（趋势图显示"质量突变"，实际是判定器变了）② A8「归档 evidence 离线重算」会失败 —— 而这是**预期行为不是缺陷**，没有该哈希就区分不出"判定器变了"与"证据坏了"。
  三个校验作用点：**run 启动**（不符则禁用 L2 指纹复用）/ **`--freeze` 写回前**（不符则拒绝固化）/ **`replay --verify` 前**（不符则直接 `BLOCKED(drift)`，不开始回放）。

## E02 实测：K8s Namespace 作 runId 隔离单元（2026-09-23 下午）

**授权**：用户明确「**仅允许创建和删除测试命名空间，不允许操作已有的相关配置**」。
**做法**：受控写操作，脚本设**三重硬守卫**——① 名字必须匹配 `^idwth-\d{8}-[0-9a-f]{6}$` ② 删除只允许作用于**本进程创建成功**的名字（内存集合）③ 删除前 GET 核验 `idwth.io/run-id` 标签 == 本次 runId。
**结果**：**20/20 通过**，写操作 5 次，**零残留**，基线 diff `added/removed/changed` 三项全空（证明未触碰已有资源）。

**核心数据**：create 201 ｜ 同名再建 **409**（可判定，不是静默成功）｜ DELETE 200 → **Terminating 6.2s** → 404 ｜ 重复 DELETE **404**（幂等，cleanup 可安全重跑）｜ `labelSelector=idwth.io/run-id=<runId>` 命中 1，对不存在 runId 命中 0。

### ★ 三条影响设计的发现

1. **❌ 证伪我自己在 PRD 评审 D1 里给的备选修法**：`created_at > run_start` **不可作为 runId 作用域判据**。对照实验：自然节奏下 `created_at − run_start = **−0.019s**`（严格 `>` 判为假阴性）／人为延迟 3s 后 `+2.293s`（通过）。
   **先排除了时钟偏移**（实测三端点偏移仅 −0.47/−0.53/−0.58s），根因是 **K8s 时间戳只到秒** —— 从 run 起始到创建只隔一次 HTTP 请求时，`created_at` 落在同一秒甚至前一秒。这是**边界脆弱判据**，且失败静默。
   → **泛化原则：凡跨系统的时间戳比较，都不能作为"这是本次产生的"判据。** 时区、精度、时钟偏移三者任一不齐即翻转。判断归属用**身份标识**（名字/标签），不用**时间先后**。
   → 连带修正：`text_contains` 必须带**完整 runId**，裸前缀 `"idwth-"` 封不住（区分不了本次与其他 run）。

2. **🆕 新建命名空间"不是空的" → 第二个假结论通道**：干净 namespace 里 `configmaps` **已有 1 个**（K8s 自动注入的 `kube-root-ca.crt`）。于是 `configmap.count == 0` 会**在全新命名空间上直接失败，而这不是应用缺陷**。
   → 与 DD-04 **镜像对称**：残留 → 假 **PASS**；自动注入 → 假 **FAIL**。同一条解法：把断言论域从「命名空间」收窄到「**本 run 创建的对象集**」，并要求 provider 记 `excluded_system_objects[]`。**新增 D19**。

3. **🆕 cleanup 的「完成」不是 DELETE 的响应码**：200 只代表"已受理"，资源仍在 `Terminating` **6.2s**。→「完成」判据必须是**终态 404**；需轮询间隔 + 超时上限（超时 → `BLOCKED(cleanup)` 不静默放过）。
   ⚠️ 同时要**显式区分**：`DELETE` 只发一次，之后只做**只读 GET 轮询** —— 这不违反「mutation 不得自动重试」，但必须写进实现注释否则会被误读。**新增 D21**。
   → CI 耗时影响：6s × N 会主导 suite；建议 case 级清业务对象、**runId 命名空间在 suite 级统一清一次**。

## 视觉 + DOM 双通道测试 Skills 矩阵（2026-09-23 晚）

**提问**：老严问「是否可以结合 JEV 完成基于视觉 + DOM 的测试 Skills 矩阵」。

**答案：能，但形式是主从不是并列。** 产出 `final/visual-dom-matrix.md`。

**三条实证（各自独立支撑同一结论"视觉不能做默认通道"）**：
1. **DOM 能证明唯一性，视觉不能** —— `matched == 1` 是可计算的整数；视觉只能给"最像的那个"，**无法表达「匹配数 > 1」这个状态** → 直接违反铁律 6（歧义即 BLOCKED）→ 视觉不得进 L1/L2。
2. **视觉慢 50–100 倍**（第三方横向实测：定位搜索框 CSS 12ms vs 视觉 950ms；提取表格 3ms vs 3200ms；~$0.003/次）→ 与「单 case P50 < 10s」目标不兼容。⚠️ **已标注为二手数据并登记 H01 待自测**。
3. **视觉产出是坐标，不可回放** —— 分辨率/DPR/滚动/响应式任一变化即失效 → 回放时必须重新调模型 → **破坏 P0 验收「回放全程零模型调用」**。

**唯一硬需求（实测支撑）**：E01 已发现 openFuyao 的 ECharts **画在 Canvas 上、DOM 里没有数据**，V1 只能整块排除图表页。**视觉 Judge 正是把它拿回来的路径**（但监控数据仍优先走 backend 断言，视觉只补「数据对但渲染错」那一层）。

**新增三条铁律**：
- **11** 视觉不能证明唯一性 → 永不进 L1/L2、**定位角色永不产生 FAIL**（只有"观察者"角色的确定性算法能产生 FAIL）。
- **12** **模型不能创造目标** —— 候选集由代码生成并编号，模型只输出集内 index。**这是「论域收窄」的第三次应用**（前两次：残留→假 PASS／系统注入→假 FAIL），三次同构，已写入记忆作为通用原则。
- **13** **视觉断言阈值必须先标定噪声下界**（连拍 N≥10 取 p95 得 `ε_base`，阈值 `> k·ε_base`，k≥3）—— 铁律 7 的视觉版。配套 **Runtime 独占 4 → 5**（新增噪声闸门校验权）。

**Skills 形状判断（关键取舍）**：**7 → 9，拒绝 14。** 模态（DOM/视觉）是**每个 skill 内部的参数**，不是新 skill —— 按模态重切会得到 7×2 个横切重复的 skill，职责边界立刻模糊（且违反"反对版本膨胀"）。只新增 2 个**人机接口性质**的：`web-visual-baseline`（基线审批流）· `web-visual-diff-triage`（差异分诊）。另新增 **3 个必须落代码**的模块：`VisualOracle` / `VisualStabilityCalibrator` / `SensitiveRegionMasker`。

**外部参照（Midscene.js，字节跳动，MIT）—— 最有价值的一条**：其**官方文档自己要求**「为降低模型假阳/假阴的风险，需要确定性校验时，应把 AI 查询与标准代码断言组合使用」。**厂商自己承认视觉断言不确定** → 我们不应比厂商更激进。其公开局限：只看 viewport 内（**DOM 反而能定位视口外元素**，又一"强项不重叠"证据）、动态渲染需显式等待、每步 500–2000 tokens。

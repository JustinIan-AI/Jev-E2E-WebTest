# 面向 BS 架构系统的系统测试工具：产品定义与 Skills 支撑方案

> 承接《JEV 系 BS 架构系统测试方案调研报告》与《复用现有浏览器状态的实现方案》
> 本文回答两个问题：**产品核心功能与形态是什么？多个 Skills 能支撑到什么程度？**
> 前置事实不变：执行臂选 CDP（Playwright `connectOverCDP`），P0 闸门已实测 14/14 通过

---

## 零、先说结论

| 问题 | 答案 |
|---|---|
| **产品核心功能** | 把「用例」编译成「确定性执行 → 三态判定 → 证据级报告 → 零模型回放」；模型只负责一件事：**控件语义映射** |
| **产品形态** | **不是"一个 CLI"，而是「常驻本地 harness + CLI 客户端 + 本地控制台」三件套** —— 因为"复用现有浏览器状态"天然需要一条长连接和一个会话账本。⚠️ **2026-10-10 裁定：本三件套未采纳 —— V1 = 纯 CLI（单进程），不做常驻服务/控制台、无前后端分离（DD-47）** |
| **多个 Skills 能支撑吗** | **能支撑"好不好用"，不能支撑"可不可信"。** 六个 skill 可覆盖交互面与知识面；执行面与判定面**必须落代码** |
| **顺序** | **不可颠倒**：引擎（P1–P4）先落地 → skills 作为加速层叠加 |

**一句话记住边界**：**Skills 决定这个工具好不好用，代码决定这个工具可不可信。**

## 一、产品定位

### 1.1 一句话定位

**寄生在开发者现有浏览器里的 BS 系统回归测试工具：用例进，证据级报告出。**

### 1.2 它不是什么（划清边界比堆功能重要）

| 不是 | 为什么 | 这条边界挡住了什么 |
|---|---|---|
| **不是 web agent** | 不追求"什么页面都能点"；追求"同一条路每次结论一致" | 挡住"让模型自己点、自己说通过"的诱惑 |
| **不是 Playwright 替代** | 是它的**上层**：补用例契约 / 判定 / 报告 / 回放 | 挡住重造浏览器驱动的浪费 |
| **不是 RPA** | 不出浏览器 | 挡住桌面/移动端需求 |
| **不是合成监控** | 不做 7×24 全站探测；面向"变更后回归" | 挡住 SLA/拨测类需求 |
| **不是测试管理平台** | 先出文件产物，不与 TestRail/Xray 深度整合 | 挡住前期集成债务 |

### 1.3 差异化三角（只有三条，其余都是实现细节）

| # | 差异化 | 解决的真实痛点 | 竞品状态 |
|---|---|---|---|
| ① | **免搭建会话** | 接管你**已登录**的 Chrome，后台标签页跑、不抢焦点 | Playwright 需重新登录；Selenium 需配 profile |
| ② | **判定不自证** | 只有确定性断言能产生 FAIL；模型说"异常"只生成候选问题 | jev-ultrafast / page-agent **两者都靠模型自述** |
| ③ | **报告是证据** | 用例原文 / 遮罩截图 / 四列对照 / 可粘贴的回放命令 | 同类工具报告多为"结果罗列"，无对照 |

> 这三条缺任何一条，产品就退化成"又一个 Playwright 封装"。

### 1.4 用户与场景

| 角色 | 关心什么 | 产品给的 |
|---|---|---|
| **测试开发**（主用户） | 写用例快、失败可复现 | `.cases` 声明式 + 一键复现命令 + 定位自愈建议 |
| **研发** | 缺陷有证据，不接受"它挂了" | 四列对照表（Expectation/Expected/Observed/Result）+ 截图 + trace |
| **测试负责人** | 结论可信、成本可控 | 三态分账 + 成本栏 + 误报率指标 |
| **CI 门禁** | 退出码稳定，不随机红 | `0/1/2/130` + 回放零模型调用 + 漂移报错 |

**核心使用时刻**（产品的存在理由）：
> 后端改了一个校验规则 → 我在自己的 Chrome 里已经登录着 staging → 敲一行命令 → 90 秒后拿到一份能直接贴进缺陷单的报告。

### 1.5 反定位：这个产品不该有的野心

| 不做 | 依据 |
|---|---|
| **不做"零用例"** | 没有断言就拒绝执行 —— *"the runner does not invent correctness criteria"*（jev-e2e）。这是产品性格，不是缺陷 |
| **不做自动修复应用缺陷** | 只出证据，不出补丁。补丁交给写代码的人 |
| **不做全兼容** | 原生桌面/CAPTCHA/canvas/支付渠道/主观视觉 —— 明确不支持并写进文档 |
| **不做"模型越强越准"** | 模型只在定位模糊处介入；产品价值来自**确定性收敛**，不是模型能力 |

## 二、核心功能：六个功能面

技术分层（九层）已在实现方案里给出；这里只讲**用户可感知的六个面**。

### F1 用例即资产 —— 声明式契约，不是编程

| 项 | 设计 |
|---|---|
| 形态 | `.cases` 文本文件，人工可读、可 Code Review、可进 Git |
| 内容 | 步骤（语义描述）+ **显式断言** + fixtures 引用 |
| 硬约束 | 无断言 → **拒绝执行**；凭据字面量 → **BLOCKED**（强制 `@fixture`） |
| 防篡改 | 8 项校验（jev-e2e 已验证），用例原文进报告可逐字比对 |

**产品含义**：用例是**资产**不是**脚本**。测试开发不写代码也能贡献用例，这是推广的前提。

### F2 接管你的浏览器 —— 免搭建会话 + 每 case 隔离

| 能力 | 实现 |
|---|---|
| 复用登录态 | `chromium.connectOverCDP('http://127.0.0.1:<port>')`，读既有 cookie/localStorage |
| 不抢焦点 | `Target.createTarget(background:true)` + `Emulation.setFocusEmulationEnabled` |
| 每 case 隔离 | `browser.newContext()`（**实测可用，cookie 隔离为 0**） |
| 强隔离兜底 | 需全新会话的 case → 独立 context；需复用会话的 → 既有 context 新 page |
| 退出干净 | `browser.close()` **只断连不杀用户浏览器**（3/3 轮实测复核） |

**产品含义**：这是整个产品的**技术护城河**。竞品要么无法复用会话，要么复用后污染用户当前页。

### F3 三级定位 —— 把模型成本压到趋零

| 级别 | 手段 | 成本 | 预期命中率 |
|---|---|---|---|
| **L1 确定性** | 语义 → ARIA role / label / text（`getByRole`） | **0** | **> 80%** |
| **L2 指纹复用** | 历史成功流程的控件快照（`plan.json.flows`） | **0** | 稳定期主体 |
| **L3 模型兜底** | 一次 JEV 投机扇出请求（TypeSafe 校验） | 1 次调用 | 长尾 |

**产品级机制 ——「学习飞轮」（本产品最被低估的资产）**：
```
L3 模型定位成功 → 控件指纹写回 plan.json → 下次同一条路走 L2（零成本）
```
于是 **模型调用量随跑次数单调递减，收敛到零**。这是相对 web agent 的根本优势：**agent 每次都重新犯错，runner 只错一次**。

产品化要求：把"固化"做成显式动作（~~控制台按钮~~ → **CLI `--freeze`**（**2026-10-10 裁定：V1 无控制台**，见 `detailed-design.md` DD-47） + 自动固化阈值 + 固化前 diff 预览），让用户看得见成本在下降。

### F4 三态判定 + 问题三分类 —— 结论可信的核心

| 判定 | 触发条件 | 是否计入 bug 检出 |
|---|---|---|
| **PASS** | 全部断言通过且求值完整 | — |
| **FAIL** | **仅**确定性断言不通过 | ✅ 计入 |
| **BLOCKED** | 控件找不到 / 作用域歧义 / 断言无法求值 / 执行中止 | ❌ **永不计入** |

**问题三分类**（JevTest 的核心贡献，必须保留）：

| `issue.source` | 含义 | 是否产生 FAIL |
|---|---|---|
| `assertion` | 确定性断言失败 → 应用缺陷 | ✅ |
| `execution` | 执行层失败（点击超时、元素遮挡） | ❌ 归 BLOCKED |
| `model` | 模型认为异常 | ❌ **恒为 candidate，需人工复核** |

**四条不可妥协的规则**：
1. 只有确定性断言能产生 FAIL —— 模型不能宣判应用有 bug。
2. BLOCKED 不计入 bug 检出（jev-e2e 基准的明确声明）。
3. 复杂度不足即 BLOCKED，**不得退化为 FAIL**。
4. 模型置信度 `< 0.6` → 降级为 `uncertain`（JevTest 的 `assessmentConfidence`）。

**产品含义**：**误报率是这类工具的生命线**。一个会随机报 FAIL 的工具，团队三天后就会忽略它。

### F5 证据级报告 —— 五要素 + 成本

| 要素 | 数据来源 | 报告呈现 |
|---|---|---|
| ① 测试用例 | `report.json.plan[].source`（**原文**） | 卡片顶部可折叠原用例 |
| ② 测试截图 | `page.screenshot({mask})` 遮罩 `input,textarea,[contenteditable],[data-private]` + fixture 明文 | 卡片底部配图；`--steps` 时动作时间轴缩略图 |
| ③ 是否通过 | `verdict` | 三色徽章（配色见下） |
| ④ 未通过原因 | `reason` + **`Expectation / Expected / Observed / Result` 四列对照** + `issues[]` | 逐条摊开"期望什么 / 实测什么" |
| ⑤ 可复现过程 | `trace.json`（逐步 before/action/after/check）+ `plan.json.flows` | "复现"按钮输出可直接粘贴的回放命令 |

**头部统计**（jev-e2e 的做法值得照抄）：总 verdict、目标 URL、case 数、总耗时、**模型请求数**、**美元成本**、实际解析到的模型 ID。

**配色**（国内约定，刻意避开红绿表通过与否）：

| 判定 | 色 | 说明 |
|---|---|---|
| PASS | 中性 / 蓝 | 与涨跌色解耦 |
| FAIL | 红 | 需关注 |
| BLOCKED | 琥珀 | 需人工介入，非应用缺陷 |

### F6 零模型回放 —— 能上 CI 门禁的前提

| 能力 | 要求 |
|---|---|
| 回放路径 | 全程零模型调用（用 `plan.json` 的控件指纹） |
| 漂移检测 | 逐步比对 `fingerprint`/断言/执行失败；不一致即 **报错并终止** |
| 原则 | *"State drift is reported instead of silently adapting the trace."*（JevTest） |
| 退出码 | `0 PASS / 1 FAIL / 2 BLOCKED 或配置错误 / 130 取消` |

> **取舍要点**：回放校验的是"状态是否漂移"，不是"结果是否一致"。漂移了说明环境变了、测试结论作废 —— 这比"跑过了就绿灯"诚实得多，也是唯一能进门禁的语义。

### F7（横向）多执行臂 —— 架构预留，不是首期功能

| 臂 | 何时用 | 状态 |
|---|---|---|
| **CDP Adapter** | 默认主干 | **P1 落地** |
| **In-page Adapter** | MFA / 无法接管 CDP / 免安装 | P5 落地，先留 `Adapter` 接口 |

两种臂共用同一套 `contracts`（用例契约 + 结果契约），因此报告层不需要知道臂的差异。

## 三、产品形态：三件套，不是单命令

### 3.1 形态判断的推理

「复用现有浏览器状态」这个核心能力，决定了形态**不能**是"一次性 CLI 进程"：

| 需求 | 一次性 CLI 的问题 | 需要什么 |
|---|---|---|
| 维护 CDP 长连接 | 每次启动都要用户先手动开 Chrome 带调试端口 | **常驻连接池** |
| 管理 tab 池与会话 lease | 进程退出即丢失 | **常驻会话账本** |
| 恢复崩溃/端口污染 | 无法自愈（实测踩过：残留进程致 `/json/version` 404） | **常驻健康守护** |
| 多个 case/多人并发 | 端口与 tab 争抢 | **调度队列** |
| 报告浏览与 plan 固化 | 只能读文件夹 | **本地控制台** |

**结论：形态是 `daemon + cli + 本地控制台`，类比 Docker（daemon+cli）而不是 Playwright（纯库）。**

### 3.2 三种形态与演进路径

> ⚠️ **状态（2026-10-10）**：本节 **形态 B（常驻服务 + 本地控制台）/ C（平台化）未采纳**。裁定 **V1 = 形态 A（纯 CLI 单进程）** —— **不做控制面、无前后端分离**。见 `PRD.md` §1.3 与 `detailed-design.md` DD-47 / DD-48。**本节与 §3.3 作为早期设想留档，不再作为规划依据。**

| 形态 | 构成 | 谁用 | 增量能力 | 何时上 |
|---|---|---|---|---|
| **A 单机 CLI** | 一个进程内嵌 harness，无 daemon | 个人开发 | 复用会话、跑用例、出报告 | **MVP / 首发** |
| **B CLI + 常驻服务 + 本地控制台**（**目标形态**） | `jev-harness`(127.0.0.1) + `jev`(cli) + 本地 Web | 测试开发团队 | tab 池、并发、控制台、plan 固化、趋势 | **团队日常回归** |
| **C 平台化** | 中心服务 + 任务队列 + 多执行节点 + 报告归档 | 企业测试平台 | 多项目/多环境/审计/权限 | 仅在接口上预留 |

> **推荐路径：A → B，C 只预留接口。** 不要一开始做 C —— 在企业级验证前，C 的复杂度是纯负债。

### 3.3 目标形态（B）的内部构成

```
┌──────────────────────────────────────────────────────────────┐
│  jev (CLI)                                                   │
│  run / replay / report / open / doctor / cases               │
│  —— 无状态；退出码即契约；--json 输出稳定 schema              │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP + JSON（唯一契约）
┌───────────────────────────▼──────────────────────────────────┐
│  jev-harness (常驻 127.0.0.1)                                 │
│  · Chrome 连接池 (connectOverCDP)   · tab 池 / 会话 lease     │
│  · 端口管理 + 崩溃恢复              · 事件总线（逐步取证）      │
│  · 用例解析 · 定位 · 断言 · 判定 · 取景（全部确定性）           │
└───────────────────────────┬──────────────────────────────────┘
                            │ 文件产物 + SQLite 索引
┌───────────────────────────▼──────────────────────────────────┐
│  runs/<runId>/                                                │
│  report.html  report.json  plan.json  trace.json  summary.json │
│  + step-N.png                                                 │
└───────────────────────────┬──────────────────────────────────┘
                            │ 只读
┌───────────────────────────▼──────────────────────────────────┐
│  本地控制台 (127.0.0.1)                                       │
│  · 报告浏览 / 候选问题审核   · plan 固化（学习飞轮入口）        │
│  · 漂移对比 / 趋势           · 一键复制复现命令                │
└──────────────────────────────────────────────────────────────┘
```

**三件套的职责边界（关键设计约束）**：

| 组件 | 只做 | 绝不做 |
|---|---|---|
| CLI | 参数解析、调 harness、格式化为人类/JSON 输出 | 不直接碰浏览器 |
| harness | 浏览器、执行、断言、判定、写盘 | 不调模型做判定 |
| 控制台 | 展示、固化操作、人审 | 不改判定结果 |

**存储选型**：文件式产物（归档友好、可进 CI artifact）+ SQLite 索引（趋势查询）。**不上 MySQL/PG** —— 单机工具引入 DB 服务是自找麻烦。

### 3.4 形态 A 的 MVP 边界（P1 交付）

| 做 | 不做 |
|---|---|
| `jev run cases/*.cases` 一条命令闭环 | ❌ 不接模型（L1 确定性定位足够跑通） |
| 复用本机 Chrome（harness 进程内） | ❌ 不做可视化录制 |
| 7 个封闭断言 + 三态判定 | ❌ 不做云端执行 |
| `report.html / report.json / trace.json / 截图` | ❌ 不做测试管理集成 |
| `--json` + 退出码 | ❌ 不做并发调度 |

**MVP 验收的唯一硬标准**：*同一 case 连跑 10 次，结论一致*。做不到就不能上 CI，门禁会随机红。

## 四、多个 Skills 能支撑吗？

### 4.1 核心判断

**能支撑"控制面"，不能支撑"数据面"。**

| 面 | 包含 | 能否 skill 化 | 原因 |
|---|---|---|---|
| **控制面**（交互与知识） | 用例创作、报告解读、失败分诊、自愈建议、稳定性诊断 | ✅ **能** | 需要理解语义、做归因、写给人看；产出是**可人工审阅的建议** |
| **数据面**（执行与判定） | 动作派发、断言、判定、截图、写盘、回放 | ❌ **不能** | 结论必须**可复现、可归档、可当门禁**；模型驱动天然非确定 |

**更锋利的一句**：
> Skills 是**给模型看的操作规程**，不是**给机器执行的运行时**。
> 凡是"结论必须可复现、可归档、可当门禁"的环节，必须落代码；
> 凡是"需要理解语义、做归因、写给人看"的环节，才适合落 skill。

### 4.2 逐能力判定表（12 项）

| # | 产品能力 | skill 可支撑 | 判定理由 |
|---|---|---|---|
| 1 | **用例编写/迁移**（PRD、接口文档、手工用例 → `.cases`） | ✅✅ **强** | 纯语义转换；产出是静态文件，错了人能看见 |
| 2 | 用例审查与拒因解释 | ✅ **中** | 校验规则必须代码实现；但"为什么被拒 + 怎么改"适合 skill |
| 3 | **动作派发**（点击、输入、导航） | ❌ **禁** | 需要确定性事件语义与超时控制；skill 无法保证执行 |
| 4 | **断言求值** | ❌ **禁（一票否决）** | 自证陷阱：让模型决定通过与否 = 产品根基崩塌 |
| 5 | **判定聚合**（三态） | ❌ **禁** | 同上；且必须可审计 |
| 6 | 截图与取证 | ❌ **禁** | 必须与判定时刻严格同步，不能"顺手截一张" |
| 7 | 报告**数据层** | ❌ **禁** | 必须由 harness 原子写入，否则报告不可信 |
| 8 | 报告**叙述层**（结论摘要、归因、趋势） | ✅✅ **强** | 模型最擅长；错了不影响判定 |
| 9 | **定位兜底**（L3） | ⚠️ **仅限 L3** | 只允许在 L1/L2 都失败时介入一次；越界即违规 |
| 10 | **回放** | ❌ **禁** | 必须零模型调用；有模型参与就不是回放 |
| 11 | **失败分诊**（真 bug / 环境漂移 / 用例错） | ✅✅ **强** | 跨证据推理，模型强项 |
| 12 | **定位自愈**（selector 修复） | ⚠️ **半** | 建议由 skill 出，**写回由 CLI 做且需人确认** |
| 13 | 造数/清理 | ⚠️ **半** | 策略与账本适合 skill；调用必须走 API 代码 |
| 14 | 同类框架审计 | ✅✅（已有 `ai-e2e-test-framework-audit`） | — |

### 4.3 六个 Skill 的设计

> 命名约定：`e2e-*`。全部放在**用户级** skills 目录，项目约定另走项目级。

| Skill | 触发时机 | 输入 | 输出 | 与引擎的契约 |
|---|---|---|---|---|
| **`e2e-case-author`** | 用户给 PRD / 接口文档 / 手工用例 / 口头描述 | 需求材料 | `.cases` 文件 + 改动说明 + 覆盖点清单 | **只写文件，不跑浏览器** |
| **`e2e-run-and-triage`** | "跑一下 / 回归 / 验证 XX" | 用例路径或标签 | 结论摘要 + 分级归因 + 下一步建议 | 只调 `jev run --json`，**只读 `report.json`**（不解析 HTML） |
| **`e2e-report-review`** | "看下报告 / 这次为什么挂" | runId | 人话摘要 + 逐 case 归因 + 建议行动 | 只读 `runs/<runId>/` 下的 JSON |
| **`e2e-locator-heal`** | 报告出现 `BLOCKED(定位失败)` 或 selector 失效 | runId + `plan.json` | 修复建议 + **待人工确认的 plan 补丁** | **不自动写回**；补丁由 `jev` 应用 |
| **`e2e-flake-triage`** | "这个 case 时好时坏" | case id | 分类结论（时序/数据污染/环境/真 flake）+ 证据 | 连跑 N 次 `jev run --json`，比对 `trace.json` |
| **`e2e-framework-audit`** | 评估同类框架 | 仓库 / 产品 | 可信度与落地性审计报告 | 只读源码（**已存在，可直接复用**） |

**每个 skill 必须内建两条红线**（写进 SKILL.md，防未来误用）：
1. **不得参与判定** —— 任何 skill 都无权把一个 case 从 BLOCKED 改判为 PASS 或 FAIL。
2. **必须声明降级路径** —— 每个 skill 都要写"没有本 skill 时，用哪条 CLI 命令完成同一件事"。

### 4.4 Skill 层与引擎层的三条硬约束

| # | 约束 | 为什么 | 违规后果 |
|---|---|---|---|
| ① | **skill 只能通过 CLI + JSON 与引擎交互**，绝不直接操作浏览器/DB/引擎内部状态 | 保证 skill 层**可替换、可移除**，引擎不依赖 skill | skill 腐烂后引擎跟着烂 |
| ② | **skill 的输出必须是"建议"，不是"结论"**（叙述性内容除外） | 判定归引擎 | 出现"skill 说通过就算通过"的隐性判定路径 |
| ③ | **skill 不得引入新的执行路径** | 防止出现"skill 自己开浏览器跑一遍"的旁路 | 报告与实际执行脱节，证据链断裂 |

**产品含义**：这套约束让 skills 成为**可插拔的体验层**——删掉全部 skill，`jev` 依然完整可用。这是长期可维护性的关键。

### 4.5 反例：用 skill 做 E2E 的典型失败形态

如果把上面这些能力全部做成 skill，会得到这样一个东西：

```
用户："帮我测一下登录"
→ agent 打开浏览器，自己点，自己判断"看起来成功了"
→ 自己截一张图丢到某个临时目录
→ 临时编一份 markdown 报告
```

**失效点（逐条对应本产品的核心功能）**：

| 失效 | 缺失的功能面 | 后果 |
|---|---|---|
| 无固定断言，每次判断标准不同 | F4 | 结论不可比、不可复现 |
| 无 trace/无指纹 | F6 | **无法回放**，回归无意义 |
| 判定靠模型自述 | F4 | **误报率不可控**，团队会忽略它 |
| 截图随手存 | F5 | 证据链断裂，报告不能进缺陷单 |
| 无退出码 | F6 | **不能上 CI** |

**这正是 jev-ultrafast 与 page-agent 的现状**——它们都缺断言层/判定层/报告层。**用 skills 去补这三层，等于把它们缺的东西用更不确定的方式重新实现一遍。**

### 4.6 最终答案

| 问题 | 答案 |
|---|---|
| 多个 skills 能支撑这个产品吗？ | **能，但只支撑体验层。** 六个 skill 覆盖用例创作、跑与分诊、报告解读、定位自愈、稳定性诊断、框架审计 |
| 能支撑到什么比例？ | **交互面 ~60–70%，可信度 ~0%。** 可信度全部来自引擎 |
| 能替代引擎吗？ | **不能，且方向反了。** 先有引擎，skills 才有意义 |
| 做 skills 的正确时机 | **P4 之后**（回放与 CI 打通后），此时 skill 有稳定契约可依赖 |
| 如果先做 skills 会怎样 | 得到一个"看起来很聪明、但结论不可信"的 demo —— 能演示，不能上生产 |

## 五、产品化路线（与实现方案的 P0–P5 对齐）

| 阶段 | 产品动作 | 形态 | Skill 层 |
|---|---|---|---|
| **P1** 打通闭环 | `jev run` 单命令闭环 + 报告五要素 | A（CLI） | — |
| **P2** 用例库与隔离 | `.cases` 解析 + fixtures + setup/cleanup + runId 隔离 | A | `e2e-case-author` 可先行（此时契约已稳定） |
| **P3** 接 JEV 定位 | 三级定位 + 学习飞轮（指纹写回） | A | — |
| **P4** 回放与 CI | 漂移检测 + 退出码 + 门禁接入 | A→B | **`e2e-run-and-triage`、`e2e-report-review`、`e2e-flake-triage`** |
| **P5** 降级臂 | in-page adapter（MFA 场景） | B | `e2e-locator-heal` |
| **P6** 团队化 | 常驻 harness + 本地控制台 + tab 池（**未采纳**，见 §3.2 状态注） | ~~B（目标）~~ | `e2e-framework-audit`（已存在，随时可用） |

> **注意 P6 的位置**：常驻 harness 是**团队化**功能，不是**跑通**功能。MVP 用形态 A 即可，不要提前付 daemon 的复杂度。

## 六、可衡量的产品指标

符合"确定性规则而非定性描述"的要求，全部可量化：

| 维度 | 指标 | 目标 | 为何是这个数 |
|---|---|---|---|
| **可信度**（生命线） | 同一 case 连跑 10 次结论一致率 | **100%** | 不达标不能上 CI（P2 闸门） |
| | FAIL 中经人工复核为真缺陷的比例 | **> 80%** | 低于此团队会开始忽略告警 |
| | BLOCKED 占比 | **< 15%** | 过高说明定位层不可用 |
| **成本** | 稳定期每 case 模型调用次数 | **≤ 0.2**（飞轮后趋零） | 学习飞轮的验收标准 |
| | 每 run 美元成本 | 有上限告警 | 防止回归期成本失控 |
| **效率** | L1 确定性定位命中率 | **> 80%** | 决定模型成本与速度 |
| | 单 case P50 耗时（纯确定性路径） | **< 10s** | 决定开发者是否愿意频繁跑 |
| **可用性** | 从 clone 到第一个 PASS | **< 30 min** | 决定推广速度 |

## 七、必须提前知道的三条风险

| 风险 | 表现 | 应对 |
|---|---|---|
| **误报率失控** | 团队三周后开始忽略报告 | 三态分账 + 模型信号恒为 candidate + 上述 80% 指标作为发布门禁 |
| **后端数据隔离被忽略** | 报告 PASS 但数据被污染，跨 case 互相影响 | *"Browser isolation alone does not isolate a shared database."* → 自建 `setup`/`cleanup` + runId 隔离（**两个参考实现都不解决**） |
| **Skill 层腐烂** | skills 逐渐内嵌判定逻辑，与引擎脱节 | §4.4 三条硬约束 + 定期审计"删掉全部 skill 后 CLI 是否仍完整可用" |
